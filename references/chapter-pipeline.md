# 章节流水线

## 写前

若 Python 3 可用，Skill 自动运行 `storyctl status` 与 `storyctl preflight`；作者不需要也不应手动调用它。若不可用，检查 `.web-story/manifest.json`、未结算工作区、正文顺序与相关摘要，并在最终报告中说明本次未执行确定性校验。

读取 L0–L3 上下文、[正文质量](prose-quality.md) 和 [连续性契约](continuity.md) 后，创建章节意图卡：POV、时间地点、章节问题、人物目标与阻力、情绪/爽点、必须推进与禁止改变事项、伏笔、结尾拉力、目标字数。补充本章相关实体的身份/属性/当前状态与来源、关键人物各自已知/误信/未知的信息及渠道、文风与段落取舍。只记录影响本章的约束，不必为每句话建立知识表。

对生活细节和明显转场，补记时代地域与人物活动背景、场景进入/离开时的关键身体和携带状态。先检查初始状态本身是否合理，再检查如何变化；第一章也不能省略这一判断。

Skill 自动用 `storyctl stage --chapter N --title 标题` 创建工作区；没有 Python 时按相同文件契约建立工作区。工作区中应有：

- `draft.md`：正文；
- `summary.md`：100–300 字、只记录正文已发生的事；
- `facts.json`：正文新增或修订的事实；
- `hooks.json`：伏笔状态变动；
- `review.json`：审稿结论。

## 起草与修订

依照意图卡写正文，以场景中的动作、感知和信息交换推进。段落节奏在起草时处理。初稿后从实际文本提取事实增量，再分别检查人物感知与认知、生活情境及章内/跨章连续性、段落阅读负担、语言模板感；具体判断见上述两份参考。连续性审读须沿场景动作走一遍，并从关键结果倒查身体、物品、空间和时间前提，不能只比对事实表中的名称。

修订未接受的草稿以满足既定设定和文风属于本轮写作，不必逐处征求确认。改掉无依据的漂移，不用新增世界规则、补造前史或静默改旧章圆场。修订后重新核对受影响的对白、事实、摘要与伏笔；若后续改稿改变审稿依据，重新审阅，不能沿用旧的 `pass`。

## 审稿与结算

先核验文件和数据格式，再进入与起草分开的审稿轮次：重读最终正文，不以意图卡或摘要代替。遵循 [审稿量表](review-rubric.md)，在 `review.json.checks` 中留下四类检查的具体依据，在 `findings` 中记录问题和处置。可由同一 Agent 切换到审稿任务执行，不要求多 Agent。

只有 `review.json` 为 `pass`、四类检查有记录、无未解决的 `blocker`、无未经作者接受的未解决 `major`，且事实与伏笔 JSON 合法时，Skill 才运行 `storyctl commit --chapter N`。脚本检查记录是否满足提交契约，不代表它能理解正文或证明事实无矛盾。没有 Python 时，按相同标准手动结算并说明。

草稿局部问题先修订；需要改变总纲、已接受正史或存在不能自行裁决的冲突时，保留 `needs_author`，说明证据和影响后请作者裁决。不要把普通润色也升级为作者审批。

提交后，Skill 自动运行 `storyctl validate`（若可用）。若派生索引或可视化将来失败，正文和已确认正史仍然有效；报告该派生视图滞后，不要回滚章节。
