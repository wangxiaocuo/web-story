# 审稿量表

审稿应输出可行动的发现，而不是泛泛而谈的评分。每条中高严重度发现必须包含位置、类型、证据、读者影响和修订建议。

## 必查维度

1. 章节是否提出、升级或解决了一个明确问题；
2. 因果是否成立，人物是否有能动选择；
3. 人物动机、能力、关系、时间地点和知识边界是否与正史相符；逐场景核对关键台词和反应的信息来源，排除只有读者能看见的文字形式、旁白或心理信息；
4. 是否兑现本章意图卡，并妥善处理必须推进项；
5. 节奏是否有推进、转折或情绪变化，而非纯解释；
6. 对白是否承担冲突、性格或信息差，而非轮流讲解；
7. 是否留下与当前冲突有关的下一章拉力；
8. 是否存在明显重复、抽象套话、过度解释或破坏既有文风的表达；对照前一至两章，检查重复的句法、反应、讲解方式和结尾套路；
9. 段落是否适合手机连续阅读，是否存在信息拥挤的连续长段，或为了短段而机械碎切；
10. 本章出现的实体身份、属性与时点状态是否逐项对过正史来源；新增事实是否来自最终正文，别称、误认和有因果依据的变化是否与真正矛盾区分。

起草或语言审稿须读 [正文质量](prose-quality.md)；涉及前文实体、设定或事实增量须读 [连续性契约](continuity.md)。这些检查都不能只凭摘要完成。

## 严重级别

- `blocker`：正史矛盾、重大因果断裂、越过内容边界；不能提交。信息越界支撑关键推理或行动时属于因果问题。
- `major`：章节承诺未兑现、人物明显失真、节奏失效，或无依据的信息越界；应修订或由作者明确接受风险。整章的模板对白、重复解释或阅读负担已损害场景时也属此级。
- `minor`：局部措辞、段落、格式或可选打磨；可提交并列入后续修订。
- `note`：偏好或备选建议；不影响提交。

## 审稿记录与放行

`review.json` 的结构如下。`checks` 四项均须写明实际检查的片段、来源或取舍，不能只写“已检查”。如果没有对白等适用内容，记录不适用的原因；不必虚构问题。其余必查维度按本章实际内容审阅，问题统一记入 `findings`。

```json
{
  "status": "pending",
  "checks": {
    "perception": "",
    "continuity": "",
    "mobile_readability": "",
    "prose_style": ""
  },
  "findings": []
}
```

`status` 使用 `pending`、`revise`、`needs_author`、`pass`。每条发现包含 `severity`、`location`、`type`、`evidence`、`reader_impact`、`suggestion`；修复后标 `resolution: "fixed"` 并在 `resolution_note` 说明改动与复核依据。确经作者接受的 `major` 标 `resolution: "accepted_by_author"`，在 `resolution_note` 记录作者决定，不能由 Agent 代为接受。未解决问题用 `resolution: "open"`（省略也视为未解决）。

已有 `blocker` 必须完成修复并复核；`major` 必须修复或取得明确接受。未经处理时不能因其他维度表现好而设为 `pass`。脚本只验证字段与处置状态，不能验证审稿证据真实性或语义正确性。旧的已结算审稿记录保留原样；尚未结算的旧工作区在下一次提交前补齐本契约，不需要重写全书。

审稿者不应把“检测是否 AI 写作”当作质量或投稿通过标准。应帮助作者做实质性修订、保持原创并记录自己的取舍。
